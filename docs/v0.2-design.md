# v0.2 — From POC to an OS

> **Status (May 2026):** **all three v0.2 pillars are closed.**
> Phase 8 (Package Manager), Phase 9 (Activity model), and Phase 10
> (Permissions) all merged. ABI is at `0.12.0`; the platform has
> moved past v0.2 into Phase 14 (browser capabilities). This
> document is preserved as the **historical design spec** for the
> v0.1 → v0.2 transition; the gap-map tables in §4 record what was
> open at the time and how each item resolved.

## 1. What v0.2 set out to be

v0.1 proved Akiva *can* run: a wasm kernel, a single Activity
painting, SavedState surviving a refresh, two real apps on the same
platform. That was a **proof of capability**.

v0.2 turned the POC into a **real-OS skeleton**. One goal: the
contract between the system and apps had to be strong enough that
the system could treat apps as first-class citizens — install,
launch, finish, kill, restore, request and enforce permissions —
without any step leaning on a scaffold-shaped hack.

UI, visuals, and the look of the home screen were **out of scope**.
Deliberate decision: the OS we had built worked; what was weak was
the *contract* with apps, not the look.

## 2. The three pillars

v0.2 was built around three coherent pillars. Each stands on its
own; together they were the bridge from "wasm runs" to "operating
system."

### Pillar 1 — Real Package Manager

**Question:** how does an app enter the system?

Earlier installation was a hack: `runtime/web/worker.js` held
`DEV_APPS = ["hello", "calculator", "tic-tac-toe"]` and
`installDevApps` fetched wasm + manifest straight to OPFS storage.
Phase 8 (Stones 8.1–8.5) replaced the entire chain: `.akv` archives
(AKPK v1), `akiva package`, `akiva install`, dynamic discovery via
the `/dev-apps/index.json` dev-server endpoint, plus
`akiva uninstall` and the upgrade / downgrade logic in
`PackageManager::install`.

v0.2 defined a real distribution format (`.akv`), full
implementation of `akiva package` and `akiva install`, and a Shell
that discovers apps from the PackageManager index — not from a
hard-coded JS list.

**Existing specs:** [`docs/manifest.md`](manifest.md),
[`docs/intents.md §9`](intents.md),
[`docs/storage.md §4`](storage.md),
[`docs/archive-format.md`](archive-format.md).

### Pillar 2 — Process / Activity model

**Question:** how do apps interact with each other and themselves?

Earlier only one activity ran on the primary surface. `SingleTask`
and `SingleInstance` returned `LaunchError::Unsupported`. There was
no Back navigation, no `start_activity_for_result`, no
`on_new_intent`. Shell could open an app but apps could not open
others — and could not return a result.

v0.2 completed the activity model: a real back stack with pop, all
four launch modes, activity-from-activity launches (explicit and
implicit intents), and `start_activity_for_result`. The full
lifecycle callbacks (`on_start` / `on_resume` / `on_pause` /
`on_stop` / `on_destroy`) all reach apps, not just `create` and
`save_state`.

**Existing specs:** [`docs/activity-model.md`](activity-model.md),
[`docs/intents.md §2-8`](intents.md),
[`ARCHITECTURE.md §3`](../ARCHITECTURE.md).

### Pillar 3 — Permissions

**Question:** who can do what?

Earlier the `PermissionController` was a shell — held a map of
grants but nobody declared, requested, or enforced. Every app
received every import the system could expose — no
`storage_sandbox` separate from `network`, no restriction on
`query_packages`.

v0.2 implemented the **Capability-via-Imports** model documented in
[`ARCHITECTURE.md §8`](../ARCHITECTURE.md): at install time the
PermissionController reads `manifest.permissions.required`, persists
grants, and at instantiation the loader builds an import map from
those grants. An app calling a function it does not have a grant
for fails to *link*, not at runtime check time. That is the
enforcement.

**Existing specs:** [`ARCHITECTURE.md §8`](../ARCHITECTURE.md),
[`docs/manifest.md §3`](manifest.md) (`[permissions]` section).

## 3. What v0.2 deliberately did **not** include

A list of conscious deferrals — not concessions:

- **Window manager / multi-window** — required a real compositor
  managing multiple surfaces; a pillar of its own. Landed in
  Phase 13.
- **System services** (notification manager, clipboard, location)
  — depend on an IPC abstraction not yet mature. Landed in Phase
  14.
- **Content Providers / URI permissions** — see
  [`docs/intents.md §11`](intents.md).
- **Broadcast Receivers / PendingIntent** — see
  [`docs/intents.md §13-14`](intents.md).
- **Runtime permission prompts (dangerous permissions)** — v0.2
  shipped install-time grants only. Camera / Location / Microphone
  are dangerous and were planned for v0.3 with a `request_permission`
  dialog. Geolocation arrived in Phase 14 with install-time grant;
  a true runtime prompt is still future work.
- **Code signing** — `signature.sig` in the manifest stayed a
  future field (`post-MVP` per [`docs/manifest.md §9`](manifest.md)).
- **Image / Input / ScrollView widgets** — consistent with the "no
  UI" decision. Notes-style apps deferred to v0.3+.
- **Network API, keyboard input, animations** — deferred per the
  "Not in MVP" section of [`ROADMAP.md`](../ROADMAP.md). Network +
  text input + animations all landed in subsequent phases.

The criterion: if an item required a new UI surface or new window
infrastructure, it was not in v0.2.

## 5. Definition of Done (achieved)

All criteria from the v0.2 sign-off are met. Reproduced here for
historical reference.

### Pillar 1
- [x] `akiva package calculator` produces `calculator.akv` containing wasm + manifest + res/.
- [x] `akiva install calculator.akv` installs into the runtime.
- [x] `runtime/web/worker.js` carries no app-specific names.
- [x] Upgrade (new > old `version_code`) + uninstall, with unit tests.
- [x] Shell renders the apps installed via the CLI.
- [x] `akiva uninstall <id>` removes everything in one pass.
- [x] Same-or-lower `version_code` upgrade is rejected.

### Pillar 2
- [x] Activity A can `start_activity(Intent::explicit("com.akiva.tictactoe", "Main"))` and Back returns to A.
- [x] All four launch modes pass the [`activity-model.md §4`](activity-model.md) semantics tests.
- [x] `start_activity_for_result` + `set_result` + `on_activity_result` work end-to-end.
- [x] `on_create` / `on_start` / `on_resume` / `on_pause` / `on_stop` / `on_destroy` all reach apps.
- [x] `system.back()` pops the top; the previous stack reaches `Resumed`.
- [x] Multi-task foregrounding through distinct `task_affinity`s.

### Pillar 3
- [x] Calculator declares `STORAGE_SANDBOX`; install records the grant; loader injects storage imports.
- [x] An app calling `start_activity` without `LAUNCH_ANY_APP` fails to instantiate.
- [x] Shell declares + receives `QUERY_PACKAGES` and `LAUNCH_ANY_APP`.
- [x] Grants persist across reboots.
- [x] Uninstall removes grants.

## 6. Build order and rationale (historical)

**1 → 2 → 3.**

- Pillar 1 first because without a real install everything else
  rested on a hack, and work on Pillars 2–3 would accumulate debt
  worth rewriting. The install flow is the seam everything passes
  through (permissions materialise at install, manifest validation
  happens at install).
- Pillar 2 second because the concrete permissions worth enforcing
  (`LAUNCH_ANY_APP`, `start_activity_for_result`) only become
  enforceable once multi-activity exists. Working on permissions
  before a complete activity model would have meant returning to
  add new grants later.
- Pillar 3 last so that by then the spec of "which imports go to
  whom" was solid — no enforcing of permissions whose API did not
  yet exist.

Each pillar received stones in the same shape as previous phases:
2–5 each, every stone independently mergeable.
