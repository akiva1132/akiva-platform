## Task 1 — State-machine audit פנימי ✅

**שאלה:** יש עוד באגים במצב-מכונה כמו ה-destroy() break? הבאג ששקט זמן רב כי לא היו tests על drivers שווה בדיקה של אחיו.

**רשימת בדיקה:**
- [x] [`activity_manager.rs::launch`](../framework/src/activity_manager.rs) — SingleTop reuse: מה קורה אם ה-top תואם ב-`(package_id, class)` אבל המצב שלו אינו `Resumed`? **מסקנה:** בפועל ה-top תמיד Resumed כי כל ה-drivers סינכרוניים; ה-reuse path לא שומר guard, אך הוספנו test שמעגן את ה-invariant (`singletop_reuse_returns_current_top_id`).
- [x] [`lib.rs::advance_through_create`](../framework/src/lib.rs) — אם `advance` מחזיר `None`, האם `try_restore_state` מופעל בטעות? **מסקנה:** לא באג. `launch_app` עושה early-return ב-SingleTop reuse (שורה 444) לפני `try_restore_state`. המקרים האחרים שבהם advance מחזיר None (unknown id, state past Created) לא מופיעים בקריאת `launch_app` אמיתית.
- [x] [`lib.rs::finish_top`](../framework/src/lib.rs) — אם `save_state_bytes()` בתוך ה-closure panics, האם ה-activity נתקע ב-`Stopped` בלי `on_destroy`? **מסקנה:** כן — זה design-level issue שתלוי במדיניות panic=abort/unwind. לא pure bug ב-state machine; נדחה עד שמוגדרת מדיניות panic (רצוי catch-and-log ב-ABI boundary). נרשום ב-ROADMAP Phase 10.
- [x] [`lib.rs::launch_app`](../framework/src/lib.rs) — stack consistency? **מסקנה:** `prev` תמיד מ-`stack.last()`, המוטציות סינכרוניות. אם `drive_to_paused(prev)` נכשל — זה silent no-op דרך `advance_to` (records/instances חסרים → None). הסטק לא ייצא לא-עקבי.
- [x] [`activity_manager.rs::advance_to`](../framework/src/activity_manager.rs) — **fragility תוקנה.** הייתה בעיה בסדר הפעולות: state הוחלף לפני בדיקת instance, אז במקרה-תיאורטי (legal transition + instance חסר) ה-record היה נשאר עם state חדש בלי callback שרץ. תוקן: הוספנו `instances.contains_key(id)` guard לפני שינוי ה-state, ונוסף test (`advance_to_on_destroyed_record_is_rejected`).
- [x] [`activity_manager.rs::destroy`](../framework/src/activity_manager.rs) — **bug אמיתי תוקן.** קריאה ל-`destroy()` מ-`Initial` הייתה מוחקת את ה-instance ומסירה את ה-entry מ-`task.stack`, למרות שאף callback לא רץ ו-state נשאר Initial (כל 3 היעדים illegal). הוספנו guard שמציב `Destroyed` כתנאי לניקוי; מלווה ב-test (`destroy_from_initial_is_full_noop`).

**הצלחה:** 2 באגים תוקנו, 4 bullets תועדו כ-"לא באג / out of scope". 3 tests חדשים, `cargo test -p akiva-framework` → 71/71 ירוק (68 קודם + 3 חדש).

**תיקונים:** `framework/src/activity_manager.rs` — reorder ב-`advance_to`, guard ב-`destroy`, 3 regression tests.

**מאמץ:** חצי יום (בפועל: ~שעתיים).

## Task 2 — Boundary review: Framework vs SDK Activity ✅

**שאלה:** יש שתי traits שנקראים `Activity` (ב-framework ו-ב-SDK), שתי `Context`/`ActivityContext`, שתי `PointerEvent`/`KeyEvent`. החתך הזה היה מכוון (wasm boundary) אבל Stone 9.4-9.5 יוסיפו עוד APIs (`start_activity_for_result`, `on_new_intent`, `on_activity_result`). האם ה-duplication יצמח, ואם כן — האם החתך עדיין נכון?

**רשימת בדיקה:**
- [x] **Inventory של duplication:** טבלה ב-[`research-activity-boundary.md §1`](research-activity-boundary.md) — 7 שורות שמראות מה משותף ומה שונה. ה-split מכוון: framework מחזיק typed `Intent`, SDK מחזיק `Canvas` + `SavedState`.
- [x] **איך wasm app מסיימת את עצמה היום?** **שאלה שנקראה loudly — התשובה: לא מסיימת.** `ActivityContext.finish_requested` קיים ב-framework, אבל ה-SDK `Context` לא חושף אותו. `WasmActivity` proxy מעביר callbacks host→app, אבל אין back-channel. זה gap קונקרטי שחוסם את Stones 9.3/9.4.
- [x] **האם יש trait משותף?** לא. `WasmActivity` הוא framework-side implementor של framework `Activity`, מפורור ל-`host.lifecycle(...)`. צד ה-SDK יש-לו `Activity` trait משלו שה-`akiva_activity!` macro מתרגם ל-`akiva_app_*` exports ישירות. אין shared trait ב-ABI boundary — רק shared *state* (lifecycle enum).
- [x] **Phase 9 API טבלה:** 5 imports חדשות + 2 exports חדשות (finish, back, start_activity, start_activity_for_result, set_result; on_new_intent, on_activity_result). כולם **דרך imports**, לא דרך context fields. הנימוק: lifetime (context fields חיים callback אחד בלבד) + WIT forward-compat (imports מתרגמים 1:1 לפונקציות interface ב-v1).
- [x] **Flat או סאב-traits?** flat. סאב-traits עם ~10 methods + 5 default no-ops הם pure overhead. Android's own Activity העדיף to stay monolithic במשך 15+ שנים.

**הצלחה:** נכתב [`docs/research-activity-boundary.md`](research-activity-boundary.md) (~230 שורות, כולל 2 קטבי בחירה + טבלת Phase 9 API + HAL signatures מתוכננות). אקשיינים:
1. `docs/abi.md §2.3` — תועדו 5 imports המתוכננים + 2 exports חדשים עם stone numbers, כ-trajectory גלוי.
2. `ROADMAP.md` Stone 9.3 — נוסף bullet מפורש לחוטי `Context::finish()` + `Context::back()`.
3. **לא** נוספו SDK stubs — stub שקט של `ctx.finish()` היה mislead את מחברי האפליקציות. Stone 9.3 מיישם end-to-end.

**מאמץ:** 2-3 שעות (בפועל: ~שעה — ה-gap של finish() קפץ מהר ברגע שקראתי את שני ה-Context structs זה ליד זה).

## Task 3 — מחקר web: Android lifecycle edge cases ✅

**שאלה:** יש ב-Android state transitions שאנחנו לא מצאנו עדיין. רוצים לוודא שה-matrix שלנו נכון לפני שבונים עליו עוד שלושה stones.

**רשימת בדיקה:**
- [x] **Created → Destroyed ישיר:** Android אכן מקצר — onStart/onResume/onPause/onStop **לא** רצים; onDestroy נקרא ישירות אחרי onCreate. **הפער אצלנו:** matrix שלנו מחייב ladder מלא; `finish_requested` שנקבע מתוך `on_create` מתעלמים ממנו עד ש-`on_resume` יצא. **WANT — Stone 9.3.**
- [x] **onRestart:** קיים כ-callback נפרד ב-Android, מופעל **רק** על Stopped→Started. רוב ה-apps לא overriding. **החלטה שלנו (מאומתת):** SKIP by design — Stopped→Started re-fires `on_start`, ואפליקציה יכולה לגזור "restart" מתוך state פנימי.
- [x] **onNewIntent:** מופעל ב-singleTop, singleTask, FLAG_ACTIVITY_SINGLE_TOP, FLAG_ACTIVITY_CLEAR_TOP. **הפער אצלנו:** SingleTop reuse היום silent swallow — ה-intent השני נעלם. **CRITICAL for Stone 9.4.**
- [x] **SingleTask clear-top:** intervening activities מקבלים full teardown (`onPause → onStop → onDestroy`), לא batch. ה-implementation אצלנו נשען על `destroy()` קיים — עבודה כמעט כולה "loop + stack fixup". **NORMAL priority for Stone 9.2.**
- [x] **Task reparenting / clearTaskOnLaunch:** עדיין active ב-2026, לא deprecated. מיועדים ל-multi-task — SKIP ל-Phase 11+. נרשם ב-`manifest.md §9` לשם reserving הרעיון בלי namespace.

**הצלחה:** נכתב [`docs/research-android-lifecycle.md`](research-android-lifecycle.md) (~220 שורות, 5 שאלות מצוטטות מ-AOSP, טבלת סיכום). אקשיין שבוצע:
1. `docs/activity-model.md` — 2 שורות חדשות ב-§2 Implementation table (Created→Destroyed shortcut ❌ Stone 9.3, on_new_intent ❌ Stone 9.4), וקישור למחקר.
2. `ROADMAP.md` Stone 9.3 — bullet חדש ל-Created→Destroyed shortcut.
3. `docs/manifest.md §9` — רשומה למאפייני task-management (Phase 11+, no namespace yet).

**מאמץ:** 2-3 שעות (בפועל: ~שעה — WebFetch + WebSearch על ה-AOSP docs פתחו לי מהיר את כל ה-5).

## Task 4 — מחקר web: WebAssembly Component Model ✅

**שאלה:** יש לנו ABI קאסטום (`hal_app_*` + `akiva_app_*`). ה-[Component Model](https://component-model.bytecodealliance.org/) הוא תקן מתגבש לאינטראקציה wasm-ל-wasm וwasm-ל-host. השאלה: **האם אנחנו בונים משהו שיחליף אותו, ואם כן — האם כדאי לעבור עכשיו כש-3 apps רצים, או להמשיך ולעבור ב-v0.3?**

**רשימת בדיקה:**
- [x] **סטטוס:** Component Model + WASI 2 shipped 2025, WASI 0.3 Feb 2026. **wit-bindgen עדיין 0.x** עם התראה מפורשת "technology preview" — הכרזת 1.0 עדיין לא קרתה. jco (browser transpiler) 1.18.1 — production-grade. Browsers: אין תמיכה native ב-Component Model; חייבים jco transpile step.
- [x] **WIT coverage:** admin APIs (lifecycle, intents, state, resources) ממפים טבעי. **Paint-op stream — לא**. רפרזנטציה של 7 opcodes/frame × 60fps כ-WIT records תגדיל bytes per frame משמעותית. Hot path worth preserving as narrow binary.
- [x] **Tooling cost:** switch ל-`wit-bindgen` דורש (1) build step חדש ב-SDK + apps, (2) loss of control (שמות exports, allocator, string encoding), (3) 0.x churn risk. jco ב-`akiva package` pipeline — עוד tooling dependency של ~40MB Node.
- [x] **Size overhead:** ~10-30% ל-modules קטנים. Hello ~50KB → ~60-80KB (+20-60%). Calculator ~300KB → ~330-370KB (+10-25%). לא אסוני, אבל ריאלי — וככל שה-app קטן יותר, ה-hit היחסי גדול יותר.
- [x] **Migration strategies:** 3 אופציות — Cold cut (v0.3/v0.4 big-bang), Gradual (hybrid v0+v1), Wait + re-evaluate (recommended).

**הצלחה:** נכתב [`docs/research-component-model.md`](research-component-model.md) (~170 שורות). החלטה: **defer to v0.4+** — נשארים על ABI v0 ל-v0.2 + v0.3. 3 re-evaluation anchors:
1. wit-bindgen מכריז 1.0 עם stability promise.
2. App קונקרטי שדורש cross-language composition / streams / WIT-native API.
3. Paint-op story שלא מפוצצת per-frame bytes.

אף אחד מה-3 לא ייפתר עד v0.3. לא נוסף ל-ROADMAP (ה-re-check ב-v0.4 review). `docs/abi.md §1.2` narrow-by-design rule נשמר כ-gate לשמירה על שחרור זול בעתיד.

**מאמץ:** 3-4 שעות (בפועל: ~50 דקות — WebSearch + WebFetch על jco/wit-bindgen החזירו הכל).

## Task 7 — CLI posture: zero-dep policy ✅

**שאלה:** CLI עומדת ב-zero-dep (68 tests, 0 deps). Stone 9+ ובמיוחד Phase 10 ידרשו ימפורטו `akiva-framework` כ-dep. **מתי להיכנע, וכמה חשיבות יש ל-policy?**

**רשימת בדיקה:**
- [x] **Moments בעתיד שבהם CLI ירצה קוד framework:**
  1. **Full manifest validation ב-`akiva package`** — היום הפיכת `manifest.toml` ל-`.akv` לא מאמתת כלום. typo מגיע ל-runtime ב-browser. `framework/src/manifest.rs::Manifest::parse` + `normalize` היו פותרים זאת.
  2. **Dry-run install** — הרצת `PackageManager::install` עם `MemoryStorage` לבדוק upgrade/downgrade reject לפני ממש לכתוב ל-disk.
  3. **Archive diff** — `akiva diff current.akv v2.akv` מצריך מחשב diff של manifests + wasm — duplication של logic שיש ב-framework.
  4. **Stone 10+ permission validation** — האם `permissions.required` מצהיר על permissions שהמערכת יודעת עליהם? `PermissionController::check` הוא ה-authority.
- [x] **עלות בפועל של framework כ-dep:** framework עצמו יש לו אפס runtime deps (אימתתי: `framework/Cargo.toml` מכיל רק serde+toml+indexmap). התוספת ל-CLI: serde (~30 crate transitive), toml (~3), indexmap (~1), ~1MB binary, ~15s compile ראשוני cold. אחרי first-compile — `cargo build -p akiva` עדיין <1s incremental. הכאב **נמוך** כרגע.
- [x] **אלטרנטיבה: `akiva-manifest` כ-crate נפרד.** שומר CLI lean בלי להתפשר על re-parse. עלות: עוד crate לתחזק, עוד manifest Cargo.toml, API surface נוסף לשמור stable. אבל במיוחד: **אין כרגע use case שדורש re-parse ברצף install**. CLI ו-framework הם שני tools נפרדים — אחד builds, שני runs.
- [x] **Functions שרק ל-CLI:** `akiva new` scaffolder, `akiva devserver` (HTTP + filesystem), `akiva build` (`cargo` wrapper) — כל אלה לא שייכות ל-framework ולעולם לא יהיו שם. ה-separation of concerns תקף.

**החלטה:** **zero-dep נשאר עד Stone 9.7 (end of Phase 9) או עד שרואים באג אמיתי שאי-validation גרם.** מעבר יהיה **Option B: extract `akiva-manifest` crate** (לא Option A: direct framework dep), כך שה-CLI נהיית dependent על ה-manifest spec אבל לא על ה-runtime. זה שומר על ה-invariant "CLI יכולה להיבנות על host בלי runtime wasm target" ומונע cyclic dependency אם בעתיד framework ירצה לעשות משהו CLI-like (לא סביר אבל).

**Trigger ל-switch:** הראשון מבין:
1. מחבר app שולח PR עם typo ב-manifest שלא נתפס ע"י CLI (רצפטר).
2. Stone 10 permission validation נחוצה בזמן `akiva package`.
3. `akiva diff` או `akiva dry-run-install` נהיה feature בקשה.

בעת ה-switch: לא big-bang. לחלץ `akiva-manifest` כ-crate חדש בתוך ה-workspace, להעביר את המבנים (`Manifest`, `validate_*`, `parse_triple`) לשם, framework מחזיק re-export. CLI תלוי רק ב-`akiva-manifest`. docs update: `docs/v0.2-design.md` + ה-commit message של ה-stone שעושה את המהלך.

**מאמץ:** 30 דקות (בפועל: ~15 דקות — decision מהיר כי אין trigger אמיתי כרגע).
