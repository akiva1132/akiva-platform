# v0.2 Review — נקודות בדיקה לפני שממשיכים Phase 9

> **מתי זה רלוונטי:** סיימנו Phase 8 + Stone 9.1. ה-destroy() bug שנתפס ב-9.1 הוא canary — סימן שיש קוד שלא נבדק מספיק לעומק. המסמך הזה הוא רשימת audit ממוקד, לא "תסקור הכל". כל סעיף הוא **task עצמאי**: אפשר לבצע אחד ולסגור לפני המשך, אפשר לבחור תת-קבוצה.

## איך משתמשים במסמך

כל task כולל:
- **שאלה** — מה בדיוק מנסים לענות
- **רשימת בדיקה** — items ספציפיים, לא blanket
- **הצלחה** — מה נחשב "סיימתי"
- **מאמץ** — הערכה גסה (30 דק' / 1-2 שעות / חצי יום / יום)
- **תלויות** — אם יש task שצריך לרוץ קודם

אחרי כל task, פתח commit אחד ("review: <topic> — findings") שמסכם מה נמצא + פתרונות שנעשו. אם לא מצאת כלום — גם זה מידע שווה לתעד.

## Task 1 — State-machine audit פנימי ✅

**שאלה:** יש עוד באגים במצב-מכונה כמו ה-destroy() break? הבאג ששקט זמן רב כי לא היו tests על drivers שווה בדיקה של אחיו.

**רשימת בדיקה:**
- [x] [`activity_manager.rs::launch`](../framework/src/activity_manager.rs) — SingleTop reuse: מה קורה אם ה-top תואם ב-`(package_id, class)` אבל המצב שלו אינו `Resumed`? **מסקנה:** בפועל ה-top תמיד Resumed כי כל ה-drivers סינכרוניים; ה-reuse path לא שומר guard, אך הוספנו test שמעגן את ה-invariant (`singletop_reuse_returns_current_top_id`).
- [x] [`lib.rs::advance_through_create`](../framework/src/lib.rs) — אם `advance` מחזיר `None`, האם `try_restore_state` מופעל בטעות? **מסקנה:** לא באג. `launch_app` עושה early-return ב-SingleTop reuse (שורה 444) לפני `try_restore_state`. המקרים האחרים שבהם advance מחזיר None (unknown id, state past Created) לא מופיעים בקריאת `launch_app` אמיתית.
- [x] [`lib.rs::finish_top`](../framework/src/lib.rs) — אם `save_state_bytes()` בתוך ה-closure panics, האם ה-activity נתקע ב-`Stopped` בלי `on_destroy`? **מסקנה:** כן — זה design-level issue שתלוי במדיניות panic=abort/unwind. לא pure bug ב-state machine; נדחה עד שמוגדרת מדיניות panic (רצוי catch-and-log ב-ABI boundary). נרשום ב-ROADMAP Phase 10.
- [x] [`lib.rs::launch_app`](../framework/src/lib.rs) — stack consistency? **מסקנה:** `prev` תמיד מ-`stack.last()`, המוטציות סינכרוניות. אם `drive_to_paused(prev)` נכשל — זה silent no-op דרך `advance_to` (records/instances חסרים → None). הסטק לא ייצא לא-עקבי.
- [x] [`activity_manager.rs::advance_to`](../framework/src/activity_manager.rs) — **fragility תוקנה.** הייתה בעיה בסדר הפעולות: state הוחלף לפני בדיקת instance, אז במקרה-תיאורטי (legal transition + instance חסר) ה-record היה נשאר עם state חדש בלי callback שרץ. תוקן: הוספנו `instances.contains_key(id)` guard לפני שינוי ה-state, ונוסף test (`advance_to_on_destroyed_record_is_rejected`).
- [x] [`activity_manager.rs::destroy`](../framework/src/activity_manager.rs) — **bug אמיתי תוקן.** קריאה ל-`destroy()` מ-`Initial` הייתה מוחקת את ה-instance ומסירה את ה-entry מ-`task.stack`, למרות שאף callback לא רץ ו-state נשאר Initial (כל 3 היעדים illegal). הוספנו guard שמציב `Destroyed` כתנאי לניקוי; מלווה ב-test (`destroy_from_initial_is_full_noop`).

**הצלחה:** 2 באגים תוקנו, 4 bullets תועדו כ-"לא באג / out of scope". 3 tests חדשים, `cargo test -p akiva-framework` → 71/71 ירוק (68 קודם + 3 חדש).

**תיקונים:** `framework/src/activity_manager.rs` — reorder ב-`advance_to`, guard ב-`destroy`, 3 regression tests.

**מאמץ:** חצי יום (בפועל: ~שעתיים).

## Task 2 — Boundary review: Framework vs SDK Activity

**שאלה:** יש שתי traits שנקראים `Activity` (ב-framework ו-ב-SDK), שתי `Context`/`ActivityContext`, שתי `PointerEvent`/`KeyEvent`. החתך הזה היה מכוון (wasm boundary) אבל Stone 9.4-9.5 יוסיפו עוד APIs (`start_activity_for_result`, `on_new_intent`, `on_activity_result`). האם ה-duplication יצמח, ואם כן — האם החתך עדיין נכון?

**רשימת בדיקה:**
- [ ] תעד: מה ב-framework::Activity ואיו ב-SDK::Activity? איפה כל אחד משמש?
- [ ] [`framework/src/activity.rs`](../framework/src/activity.rs) יש `finish_requested` ו-`launch_requested` ב-`ActivityContext`. [`sdk-rust/src/activity.rs`](../sdk-rust/src/activity.rs)::`Context` אין. **איך wasm app מסיימת את עצמה היום?** הכי מעניין לענות. גם — אפליקציה יכולה לבקש `start_activity`? אם לא — איך Phase 9.4 אמור לעבוד?
- [ ] האם יש trait חלופי (`WasmActivity` הוא implementor ב-framework, מה SDK לוקח?) או שהגשר נבנה רק דרך host-imports?
- [ ] רשום את כל השדות שיתווספו ל-`Context` ב-stones 9.3-9.6 (`back()`, `start_activity`, `start_activity_for_result`, `activity_result`). איזה יעברו דרך ה-context וסיזה דרך imports נפרדים?
- [ ] החלטה: האם לפצל ל-sub-traits (`LifecycleActivity`, `ResultReceiver`) או להשאיר flat?

**מחקר חיצוני (משתלב ב-Task 3):** איך React Native עושה את הגבול בין host ל-app? איך Android's `Activity` באמת בנויה (inheritance? composition? lots of hooks?). איזה חלק של `android.app.Activity` אנחנו דוחים?

**הצלחה:** מסמך קצר (~200-300 מילים) שמסכם:
1. מה ה-duplication הנוכחי
2. מה היה יתווסף ב-stones 9.3-9.6
3. החלטה ארכיטקטונית: להמשיך flat? לפצל? להכניס proxy generation (macro)?
4. אם שינוי נדרש — רושם של רשומה ב-ROADMAP ("9.x: refactor boundary before 9.4").

**מאמץ:** 2-3 שעות.

## Task 3 — מחקר web: Android lifecycle edge cases

**שאלה:** יש ב-Android state transitions שאנחנו לא מצאנו עדיין. רוצים לוודא שה-matrix שלנו נכון לפני שבונים עליו עוד שלושה stones.

**רשימת בדיקה:**
- [ ] **Created → Destroyed ישיר:** ב-Android, אם `finish()` נקרא בתוך `onCreate`, מה בדיוק קורה? האם onStart/onResume נקראים או לא? מסמכים: [Activity lifecycle](https://developer.android.com/guide/components/activities/activity-lifecycle), AOSP [ActivityThread.java](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/master/core/java/android/app/ActivityThread.java).
- [ ] **onRestart:** האם באמת קיים ב-Android כ-callback נפרד, ו-אם כן — האם יש חשיבות להפרדה שלו מ-`onStart`? אנחנו היום מרכזים את שניהם ב-`on_start` — האם זה חסר?
- [ ] **onNewIntent:** מתי בדיוק זה נקרא (SingleTop only? SingleTask? SingleInstance?) ואיך זה משתלב ב-state machine? רלוונטי ל-Stone 9.4.
- [ ] **SingleTask:** "clear top" — האם ה-activities שמעל ה-SingleTask target מקבלים `onPause → onStop → onDestroy` במפורש, או שהם פשוט נמחקים ב-batch? חשוב ל-Stone 9.2.
- [ ] **Back stack:** האם Android שומר "task reparenting" או `clearTaskOnLaunch`? זה feature שאנחנו אמורים להוסיף ל-roadmap או מתעלמים?

**הצלחה:** מסמך `docs/research-android-lifecycle.md` (חדש) שמכיל:
1. תשובה קצרה לכל 5 שאלות עם ציטוטים + קישורים
2. טבלה: מה ל-Android יש שלנו אין
3. דירוג: כל אחד הוא "critical/want/skip" עם נימוק

**מאמץ:** 2-3 שעות (קריאה, לא כתיבת קוד).

## Task 4 — מחקר web: WebAssembly Component Model

**שאלה:** יש לנו ABI קאסטום (`hal_app_*` + `akiva_app_*`). ה-[Component Model](https://component-model.bytecodealliance.org/) הוא תקן מתגבש לאינטראקציה wasm-ל-wasm וwasm-ל-host. השאלה: **האם אנחנו בונים משהו שיחליף אותו, ואם כן — האם כדאי לעבור עכשיו כש-8 apps רצים, או להמשיך ולעבור ב-v0.3?**

**רשימת בדיקה:**
- [ ] מה הסטטוס של Component Model היום (אפריל 2026)? production-ready? preview? בטוח לסמוך?
- [ ] WIT (Wasm Interface Types): מה ה-coverage (strings, structs, records, option<T>, streams)? האם ה-API שלנו (מכניס struct SurfaceMetrics, bytes, callback events) ניתן לביטוי ב-WIT היום?
- [ ] Tooling: `wit-bindgen` תומך ב-Rust. האם ה-SDK שלנו יכול להיכתב מול WIT? כמה loss של control יש בזה?
- [ ] Size overhead: app wasm שמשתמש ב-Component Model בדרך כלל גדול ב-X%. מה ה-X ההיום?
- [ ] אסטרטגיות migration: האם אפשר migration הדרגתי (לשמור ABI הקיים + להוסיף Components חדשות), או חייבים cold-cut?

**הצלחה:** מסמך `docs/research-component-model.md` (חדש) עם:
1. סטטוס עדכני + ציטוטים
2. חישוב זמן/מאמץ של migration מ-ABI הנוכחי
3. החלטה: "לעבור ב-v0.3" / "לעבור עכשיו" / "לא לעבור — ולמה ABI קאסטום עדיין נכון ל-MVP"
4. אם "לעבור ב-v0.3" — רשומה ב-ROADMAP שלב 13+

**מאמץ:** 3-4 שעות (מחקר + החלטה).

## Task 7 — CLI posture: zero-dep policy

**שאלה:** CLI עומדת ב-zero-dep (68 tests, 0 deps). Stone 9+ ובמיוחד Phase 10 ידרשו ימפורטו `akiva-framework` כ-dep. **מתי להיכנע, וכמה חשיבות יש ל-policy?**

**רשימת בדיקה:**
- [ ] רשום את ה-moments ב-Phase 9/10 שבהם CLI יצטרך פונקציה מ-framework (בכל הראות: `PackageManager::install` validation; manifest parse; semver check; permission resolution).
- [ ] מה העלות בפועל של הוספת framework כ-dep? (serde + toml + indexmap — ~300KB binary, ~30s compile זמן ראשוני). האם זה כואב?
- [ ] אלטרנטיבה: האם לחלץ `akiva-manifest` כ-crate נפרד שגם CLI וגם framework תלויים בו? זה ייקר re-parse ברצפטים של install, אבל שומר על CLI lean.
- [ ] יש פונקציות שנרצה ב-CLI שלא קיימות ב-framework? (למשל: dry-run install, diff בין archive ל-installed package)

**הצלחה:** החלטה מודעת, מתועדת: "zero-dep נשאר עד Stone X, ואז משתנה ל-Y". רשום ב-commit message של ה-stone הבא שעושה את ה-switch.

**מאמץ:** 30 דקות דיון, אם לא כתיבת קוד.
